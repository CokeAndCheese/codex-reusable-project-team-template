# Runtime Controls and Task Lifecycle

选择或变更速度、创建/派生任务、使用临时 Agent，或审计侧栏中的重复角色时读取本文件。

## 1. 四个独立控制轴

每次派单必须把以下字段分开处理：

1. `tier`：项目定义的能力等级。
2. `model`：运行时接受的精确模型 ID。
3. `reasoning`：该模型的推理强度。
4. `speed` / `service tier`：Standard 或 Fast 等服务速度。

`speed` 不属于 `tier`，也不等于 `reasoning`。不得把 Standard 映射成 `medium`，不得用降低 reasoning 冒充切回 Standard，也不得根据模型名猜测服务速度。

项目的用户可见规范值使用：

- `standard`：默认速度；运行时配置通常对应 `service_tier = "default"`。
- `fast`：加速服务；只有项目策略允许且当前运行时支持时才可请求。不同工具可能把运行时值表示为 `fast` 或 `priority`，必须按工具实际 schema 映射。

新建或同步的策略默认 `standard`。Fast 的成本授权由 `service_tier_policy.fast_authorization` 决定；产品经理只能在该边界内选择。

## 2. 速度应用与证据

先核对当前目标工具是否有独立的 `service_tier` / speed 参数，再选择一种可审计状态：

- `explicit_tool_argument`：工具接受速度参数，且调用回执确认该参数已提交。
- `inherited_verified_config`：已只读核对当前生效配置；目标没有已知更高优先级的任务级覆盖。
- `manual_action_required`：工具不能修改目标任务速度，需要用户在目标任务的速度选择器或受支持的 `/fast` 控制中操作。
- `requested_unverified`：只记录了意图，无法观测目标任务的实际速度。
- `not_requested`：本次派单不改变速度。

`requested_unverified` 绝不能写成“已切换”。当用户明确要求本次先切换速度时，`manual_action_required` 或 `requested_unverified` 会关闭该次速度变更门禁；先返回准确的手动动作，再继续需要该速度前置条件的派单。

配置核对只读取与速度有关的键，避免输出令牌或其他秘密。用户级 `service_tier = "default"` 可以证明默认偏好是 Standard，但不能证明已有任务不存在显式覆盖。新任务默认值、当前任务覆盖和单次派单请求必须分别记录。

不要发送没有工作内容的空消息只为改速度。若运行时仅支持 model/reasoning、不支持 service tier，可以照常派发不要求速度变更的工作，但必须把速度状态写成 `not_requested` 或 `requested_unverified`，不得伪造已应用证据。

## 3. 任务拓扑与身份门禁

项目任务列表必须满足：

- 一个项目只有一个生效产品经理总控任务和一个对应 Thread ID。
- 每个获批长期角色只有一个生效任务；同名、同职责或重复 Profile 先消歧。
- 临时执行单元不是“子项目总控”，不得使用或继承 `项目名产品经理-项目总控` 标题。
- 用户可见任务、临时 Agent、归档记录和长期编制必须分开登记。

真实派单前，用任务列表、`ORG_CHART.md` 和 Registry 交叉核对 ID；不能只按标题猜测。若同一项目出现多个总控标题，返回 `STOP_DUPLICATE_PROJECT_CONTROL_IDENTITY`，只允许原 Registry 中的唯一总控继续协调；其他项进入重命名/归档候选，不得继续以总控身份派单。

## 4. 创建、派生与独立 QA

临时子任务默认使用产品提供的轻量子 Agent，并使用新上下文；它完成后交回，不作为用户侧长期任务保留。

- `create_thread` 用于用户明确要求的新长期或独立用户任务，不用来实现普通内部子任务。
- `fork_thread` 不作为临时 QA 的默认手段。Fork 会继承来源任务的已完成历史和通常的标题，既会污染独立上下文，也容易制造重复总控。
- 独立 QA 不从产品经理或实现者任务 fork。优先使用已登记长期 QA；确需一次性独立视角时使用 fresh-context Reviewer/Agent。
- 如果工具或环境迫使使用用户可见 fork，必须先有相应授权；创建后、发送任何工作前立即重命名为唯一临时名称，并记录 parent、child、一次性范围、同步对象和关闭方式。不能完成重命名就停止。

临时名称建议：`临时QA-{{WORK_PACKAGE}}-{{PURPOSE}}`、`临时复核-{{WORK_PACKAGE}}-{{PURPOSE}}`。名称不得包含“产品经理-项目总控”，也不得冒充长期角色的精确名称。

## 5. 重试与数量控制

- 同一映射职责默认最多一个活动临时 Agent；存在未交回项时不得再建一个。
- 普通返工、命令失败、额度不足、上下文较长或 QA 装置缺陷，优先在同一长期角色/临时 Agent 中继续，不是创建新任务的充分理由。
- 只有证据证明上下文污染、独立性失效或环境隔离无法恢复时，才可替换一次；先关闭前一个执行单元并记录原因。
- 同一工作包出现第二次替换请求时返回 `STOP_REPEATED_TEMPORARY_REPLACEMENT`。先由产品经理审查测试装置、权限、环境和工作包设计；需要继续建立用户可见任务时请求用户决定。

长期 QA 存在且可用时，重复创建临时 QA 属于治理漂移，即使每次都写了例外说明也不能因此自动合规。

## 6. 关闭与清理

临时执行单元完成后必须：

1. 把结论和证据同步到长期责任角色或产品经理。
2. 清除写入权、临时 override、未完成状态和敏感临时数据。
3. 将轻量 Agent 标记完成；用户可见临时任务按已批准的生命周期策略归档，未获归档授权时标记 `待归档` 并集中向用户请求一次决定。
4. 从“当前活动任务”视图移除，但保留必要审计索引；不得让历史临时任务继续占用长期角色名称。

归档是可恢复的组织整理，不等于删除证据。不要自动删除任务或仓库事实源。

## 7. 审计分级

- P0：多个生效总控、临时任务以总控身份派单、未授权任务创建、独立 QA 继承实现/总控上下文后仍声称独立。
- P1：已有长期角色却重复创建临时 Agent、同一职责多个活动临时项、完成后未收口、任务标题与 Registry 身份不一致、速度请求被误报为已应用。
- P2：历史任务已正确关闭和归档，但审计索引或展示说明不清。

审计默认只报告，不重命名、归档或删除。只有用户明确要求修复，或已有项目策略授权对应生命周期动作时，才执行可恢复的整理。
