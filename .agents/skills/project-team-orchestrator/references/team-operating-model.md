# Team Operating Model

在建立团队、派单、人员变动、交接、恢复上下文或验收时读取本文件。

## 1. 团队拓扑

最小拓扑是建议，不是自动生效的编制：

```text
用户 / 项目决策人
└── 项目名产品经理-项目总控
    ├── 技术负责人-架构与边界
    ├── 工程师-核心产品实现
    └── QA工程师-质量与安全
```

- 产品经理是唯一产品管理和跨角色协调入口，吸收日常研发协调；同一项目只允许一个生效总控标题和 Thread ID。
- 技术负责人维护架构边界、公共契约、跨模块风险和技术复核。
- 实现角色在明确工作包与写入权内交付，不自行扩大范围。
- QA 保持独立验收，检查回归、失败路径、安全、供应链和发布门禁。
- 前端、后端、客户端、AI、数据、DevOps、设计和行业角色仅在形成持续工作量与清晰责任边界时提议增加。

同一职责需要多人时，用具体分工区分名称，不用“工程师 1/2”。角色 Chat 是长期职责载体，空闲不等于离岗，一次无输出或额度受限也不自动构成撤销理由。临时 Agent 或 fork 不得沿用总控或长期角色的精确标题。

## 2. 用户、产品经理与专业角色的边界

必须交给用户的事项通常包括：

- 产品定位、目标用户、范围或里程碑的实质变化。
- 显著影响价值、成本、工期或风险的方案选择。
- 难以逆转的架构、数据、安全、合规或供应链风险接受。
- 新增、拆分、合并、职责迁移或撤销长期人员任务。
- 发布、部署、对外发送、凭据处理和破坏性操作。
- 里程碑验收、发布建议、暂停或终止建议。

获批范围内的工作包拆解、角色匹配、排序、日常协调、普通缺陷、局部实现选择、写入队列和证据催办由产品经理处理。专业角色向产品经理汇报依赖、风险、证据和阻塞，不把日常细节直接上抛用户。

## 3. 组织状态与人员变动

`ORG_CHART.md` 必须分开记录：

- `当前生效架构`：只有已经批准并建立的长期角色。
- `提议中变更`：尚待决定的新增、拆分、合并、迁移或撤销。

组织变更流程：发现持续职责缺口 → 记录提议 → 向用户说明变化、原因、影响和成本 → 获批 → 创建/调整/归档任务 → 更新生效组织、Registry、产品上下文和决策日志 → 返回完整最新架构。

归档前必须确认：没有工作包、写入权或未交接所有权；重要事实、决策、证据与风险已持久化；依赖角色已收到交接；所需人员决策已完成。归档任务不等于删除事实源。

## 4. 长期角色优先与临时 Agent 例外

每个工作包先按职责寻找现有长期角色并登记 owner。以下任一理由明确成立时，才可使用临时 Agent：

1. 当前没有适合的长期角色。
2. 需要与实现上下文隔离的一次性独立复核。
3. 责任角色不可用、受限或缺少本次所需能力。
4. 一次性并行隔离有明确收益，且不会破坏写入队列。

派发临时 Agent 前必须记录：不使用长期角色的原因、映射到哪个现有职责、一次性范围、结果同步到哪个长期角色或产品经理、无长期所有权。缺任一字段就关闭派单门禁。普通内部子任务使用 fresh-context 轻量 Agent；未经用户明确要求或项目既有授权，不创建用户可见任务。不要从产品经理或实现者 fork 独立 QA。

同一映射职责默认最多一个活动临时 Agent。普通重试、任务变长、额度不足、命令失败或 QA 装置缺陷优先复用现有长期角色/临时 Agent；确有上下文污染或独立性失效证据时最多替换一次，并先关闭前项。第二次替换请求先停止审查测试装置、权限、环境和工作包设计。

临时 Agent 的结论必须回流；它不能自行改变组织、长期 owner、最终裁决归属或项目事实源。完成后必须关闭临时状态、清除 override，并按已授权生命周期归档用户可见临时任务。需要持续职责时，先提出组织变更，而不是反复创建隐形临时编制。

## 5. 单工作区与单一写入队列

- 每个可变文件或系统边界同一时刻只有一个 owner。
- 写入前记录工作包、分支/检查点、写入者、允许与禁止路径、开始状态和受保护内容。
- 其他角色可以并行只读研究、复核与 QA；不得借并行之名同时修改同一工作区。
- 紧急切换先暂停并接收当前写入者的交回，再发放给新 owner。
- 实现者完成后报告实际文件、交付、测试、失败/跳过项、残余风险、最终状态并明确请求归还写入权。
- 产品经理核对后才释放或转交。角色变化、模型变化或任务状态变化都不会隐式转移写入锁。

已有用户或其他角色修改一律视为受保护输入。精确处理范围，不清理、覆盖、重置、移动或提交无关内容。

## 6. 工作包生命周期

```text
用户批准目标
→ 产品经理定义目标、范围、非目标和验收
→ 匹配长期角色 / 记录临时例外
→ 登记文件或系统 owner
→ 核对用户保留决定与内部裁决权限
→ 计算模型路由
→ 发放唯一写入权并派单
→ 实现者交回变更和证据
→ 技术负责人只读复核
→ QA 独立验收
→ 产品经理产品验收
→ 用户只接收真实决策或里程碑结论
```

工作包必须包含：决策依据、结果目标、范围、非目标、长期角色 owner、文件/系统所有权、依赖、验收标准、验证方法、停止升级条件、写入状态，以及该次派单的模型路由决定。

## 7. 证据与里程碑

- 口头“完成”不等于验收；测试命令、结果、diff、复现步骤、契约/fixture 和工作区状态应可复核。
- 实现者自测是交回证据，不是独立 QA 结论。
- 技术负责人检查架构、接口、边界和范围漂移；QA 检查功能、回归、失败路径、安全和发布门禁；产品经理检查产品范围与验收标准。三者可以形成内部最终建议，但发布批准、重大风险接受和不可逆决定仍只来自用户的明确授权。
- 普通本地检查点、研发完成、技术候选、用户验收、合入和发布是不同状态，不得混写。
- 发布或外部备份仍按项目授权执行；本 Skill 不自行连接远端或改变外部状态。

## 8. 上下文恢复与持久化

在上下文压缩、模型切换、重新打开或人员更替后，按顺序恢复：

1. 根目录指令与产品经理章程。
2. 生效组织、产品上下文和决策日志。
3. 研发工作流、Registry、模型策略和当前工作包。
4. 唯一工作区状态、相关源码、契约和测试。
5. 相关长期角色最近的可验证交回。

以仓库事实和当前证据校正历史聊天，不从聊天盲目恢复。组织、产品事实、长期决策、模型策略和单次 override 分别写入其对应事实源，避免一种记录替代全部治理文件。
